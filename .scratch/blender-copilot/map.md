# Map: Blender Copilot chat panel

`wayfinder:map` — the canonical artifact for this effort. Tickets are child issues under `issues/`. This map is an **index**, not a store: a decision lives in exactly one place, its ticket, and this map only gists it and links.

## Destination

A working vertical slice, running in Blender 5.2.2: an extension that opens a chat panel **inside Blender**, runs a multi-tool agent loop against an OpenAI-compatible API, and executes model-authored `bpy` in-process — with **one Ctrl+Z per agent turn**, so a turn can be walked back in a single step.

> **Amended 2026-09-25, and ratified the same day. Nothing in this sentence is provisional any more.**
>
> **Settled, against a resolved ticket.** The sentence formerly said "with a *per-call* undo step so any run can be walked back with Ctrl+Z". *Per-call* is stale: what *What replaces undo as the recovery mechanism?* decided is one unified push per **user turn**, at the **end**, in a `finally`. "Any run can be walked back" was an overclaim and is gone — the pushed step covers local `bpy.data` only; Global Undo off **pauses** auto-run instead of being covered by it — measured, and `bpy.ops.ed.undo()` *raises* in that state; and an active edit-mode object is now **measured too**: a push there records nothing usable and the following undo deletes the object (see *Confirm the four undo cases in a GUI*).
>
> **The scene-only narrowing was proposed and REJECTED by the project owner.** Auto-run stays **unscoped**: model-authored `bpy` runs with no approval gate, and the capability restriction that *The capability boundary for model-authored code* specified is **not built**. The rejection is coherent with the measurement rather than contrary to it — that ticket's own probe showed the guard does not contain (2 escapes in 77 attempts, both by introspection rather than through any named path), and a gate whose own evidence shows it does not gate buys false confidence. What follows from the rejection is recorded without softening in *What replaces undo as the recovery mechanism?* › Ratification: with no restriction installed, auto-run code has full filesystem access **including the plaintext API key** that *Where the API key lives, and how the user sets it* ratified into `userpref.blend`, and `bpy.app.handlers`/`timers` are open to it, so a turn can register work that outlives the turn and that the end-of-turn push cannot reach.

## Notes

**Domain.** A Blender extension (Python 3.13.13, bundled with Blender) that hosts its own agent loop. Target is the **installed** `/Applications/Blender.app` = **5.2.2**. The 5.3.0-alpha source clone at `/Users/user/Projects/blender` is **read-only reference**; it is unbuilt and off-limits.

**Execution is carried into this map.** Wayfinder plans by default, but this effort's destination is explicitly *a working vertical slice*, so tickets here legitimately build code rather than only deciding.

**Ratification status, 2026-09-25.** A human reviewed every provisional decision and ruled on all of them, which is the first time any decision in this effort was made by a person rather than an agent. **Fifteen items were accepted as written; one was rejected** — the approval gate — and that rejection is recorded in *What replaces undo as the recovery mechanism?* › Ratification and reflected throughout these Notes. *The capability boundary for model-authored code* is **set aside**: its mechanism is not built, its measurement and its factual corrections stand. Nothing in this map is provisional any more. The record is [docs/ratification.md](../../docs/ratification.md).

**Standing decisions settled while charting** (binding on every session; not tickets, so not in Decisions-so-far):

- **The agent loop runs in Blender's Python process.** No Node sidecar, no socket, no file-mailbox bridge, no IPC. Live `bpy.context` is free by construction — prior art needed an entire bridge plan to get what this design gets for nothing.
- **HTTP via bundled `requests` + `certifi`.** One OpenAI-compatible backend, **named 2026-09-25: DeepSeek** — base URL `https://api.deepseek.com`, OpenAI format, models **`deepseek-flash`** and **`deepseek-v4-pro`**, **1M-token context**, tool calls and JSON output supported (read live from `api-docs.deepseek.com`). Note the naming trap: the older `deepseek-v4-flash` is still *accepted* but is **remapped to a retired model**, which is a concrete reason not to hard-code a string from memory. *Verified:* Blender's bundled Python reaches `https://api.openai.com/v1/models` (HTTP 401 = TLS and reachability fine). `httpx`/`openai`/`anthropic`/`keyring` are **not** bundled; `requests`/`certifi` **are**. No wheel needed.
- **Three tools:** `run_blender_python` (workhorse), `get_scene_info`, `get_rna_info`. *RATIFIED 2026-09-25:* *What the prompt teaches the model about Blender* keeps it at three by adding a `guide` kind to `get_rna_info` rather than a fourth tool, so the long tail of Blender idioms is not paid for in every prompt. **That ticket's `{capability}` line is moot**, however — the restriction it would have described was rejected, so the prompt has nothing to declare.
- **Auto-run, unscoped — RATIFIED 2026-09-25.** Model-authored `bpy` auto-runs with **no approval gate and no capability restriction**. The proposal to demote it to "scene-only Python with a default-off gate" came from *What replaces undo as the recovery mechanism?* §6, was specified by *The capability boundary for model-authored code*, and was **rejected by the project owner** on the strength of that ticket's own probe: the guard is hygiene, not containment. **So, plainly:** recovery is the **memfile undo stack** — **one step per user turn, at the end, in a `finally`, only if the turn mutated** — and it reaches **local `bpy.data` only**: never files, subprocesses, network, preferences or Python state. Auto-run code can read the **plaintext API key** in `userpref.blend` and send it anywhere, and `bpy.app.handlers`/`bpy.app.timers` let a turn register work that outlives the turn and the session. These are consequences of ratified decisions rather than defects in them, and they are written down here because this map is what later sessions read. The `.blend` recovery copy is opt-in, once per session.
- **Context:** minimal live summary injected per turn; detail pulled by tool call. Never dump the scene. *Placement corrected by [How a conversation degrades as context grows](issues/14-conversation-degradation.md): the summary is the **trailing** message, not index 0 —* the stable base prompt stays at index 0 so the provider's cache prefix holds across turns.
- **Proper extension from day one:** `blender_manifest.toml`, `[permissions] network`, `blender_version_min = "5.2.0"`.
- **Hard constraints to design around:** `bpy` is main-thread-only; `bpy.app.timers` and modal operators only pump from the GUI event loop (never under `blender -b`); an addon **cannot register a new space type**, only attach to existing ones.
- **Verified the hard way, after the research tickets closed** (detail in Decisions so far): Python-initiated operators **never push undo**; `bpy.app.online_access` and even `--offline-mode` do **not** block Python sockets, so the manifest's network permission is a *declaration, not a sandbox*; `UILayout.textbox()` **does** exist in 5.2.2 and is our multi-line input; `UILayout` has **no rich text** in 5.2.2, so code and tool output render as plain text.
- **Both reopened decisions are closed, and both are ratified.** *Transport* → a **subprocess**: Blender's own bundled `python3.13` launched as `sys.executable <pkg>/_worker.py`, newline-delimited JSON over stdin/stdout; the docs' own example of *unsupported* usage is precisely the long-lived thread plus repeating timer, which is why the thread loses. *Recovery* → the memfile stack with turn-level pushes, **ratified with item 6 rejected** — see the auto-run bullet above for what that does and does not leave in force.

- **The Destination sentence was amended on 2026-09-25, and the rule for amending it was rewritten the same day** — see the note under Destination. The old rule, "never touch the anchor while its premise is provisional", produced an anchor stating **per-call undo**, which *What replaces undo as the recovery mechanism?* had already overturned; a false anchor is read first and believed by every later session. New rule: a clause contradicted by a **resolved** ticket is corrected immediately; a clause resting on an **unratified** decision is written in the provisional form with the doubt attached inline; and once a human rules, the ruling replaces the hedge outright — **including when the ruling is a rejection**, which is what happened here.

- **Charted and not yet worked.** Graduated by the first sweep: *The capability boundary for model-authored code* and *How a conversation degrades as context grows* — both now **resolved**. *Confirm the four undo cases in a GUI* is **resolved** — measured 2026-09-26; it confirmed §1's push discipline through its own negative control and corrected §4 on both counts. Graduated by the second sweep, after those two closed and both reported the same gap: *The first live send against a real provider* (`human-required` — it needs a **credential**, and nothing in this effort has ever talked to an API), *Runaway and hang protection: what can actually be stopped* (ordinary work — both ticket 12 and ticket 13 hand the UI an honesty requirement and neither specifies what it says), and *Whose state is it when more than one panel is open* (ordinary work — sharpened by ticket 14's store/projection split and ticket 08 making the panel stateful). Any ticket at `Status: human-required` is excluded from frontier scans by protocol, so no sweep will hand it to an instance. **All three then closed the same night — the live send on 2026-09-26, hang protection and multi-panel ownership before it. The frontier is empty: all eighteen tickets are resolved.** What remains is not a ticket: ticket 08's visual pass and ticket 17's `ed.undo()`-after-interrupt case both need a screen and are listed for a human in `docs/ratification.md`.

**Skills every session should consult.** HITL tickets: `grilling` + `domain-modeling`. Research tickets: `research`. Prototype tickets: `prototype`. Take them one ticket per session.

**Tracker:** local-markdown, rooted at `.scratch/blender-copilot/`. Check `research/*.md` before asserting a fact; several are already verified against source or by running Blender.

## Decisions so far

<!-- the index: one line per closed ticket, enough to judge relevance, then zoom the link for detail the ticket holds -->

- [What can a Blender 5.2 panel actually render and accept?](issues/01-panel-mechanics.md): host the panel in the 3D Viewport sidebar; repaint from a timer ending in `region.tag_redraw()`; `UILayout.textbox()` is a real multi-line input; panels cannot scroll and have no rich text.
- [What exactly happens when we exec model code, and what does undo cover?](issues/02-code-execution-and-undo.md): Python-initiated operators never push undo; undo reaches only local `bpy.data` after an explicit push; network permission is a declaration rather than a sandbox — so the recovery design had to be reopened.
- [How do we call the API off-thread and stream the reply into the UI?](issues/03-networking-and-threading.md): worker thread plus a queue drained by a timer, with `requests` SSE and fragmented tool-call accumulation — but the docs forbid `bpy` during threads and bundled code uses a subprocess, so transport needs its own decision.
- [Build the cheapest installable extension that proves the panel](issues/07-panel-shell-prototype.md): the panel exists and installs in Blender 5.2.2; sidebar host, `textbox` input and a change-only repaint timer all verified by running Blender. The visual judgement moved to the conversation-UX ticket.
- [Where chat history lives](issues/04-chat-history-storage.md): JSON under `extension_path_user(..., "conversations")`, scoped per `.blend` path with alias-on-Save-As; **never** inside a `.blend` — a `Text` datablock was *verified* to persist and travel, which disqualifies it — capped at 200 messages / 1 MiB with whole-turn pruning.
- [Where the API key lives, and how the user sets it](issues/05-api-key-storage.md): an addon-preferences `PASSWORD` field with an env var that overrides it; plaintext in `userpref.blend` is accepted *out loud* because `SKIP_SAVE` was verified **not** to prevent persistence; the model name ships empty and Send refuses until it is filled in.
- [The three tools' contracts](issues/06-tool-contracts.md): one JSON envelope and one shared 8,000-char cap; `run_blender_python` gets a **fresh namespace** per call plus a required `purpose`, and always returns the full traceback; `get_scene_info` never dumps the scene (counts + a bounded list + a `truncated` flag); `get_rna_info` is exact-name lookup against a cached enumeration because `getattr` lies about existence.
- [How a conversation is laid out and controlled](issues/08-panel-conversation-ux.md): the `boxes` layout — labelled user turns, one bordered box per assistant turn, permanent tool rows, errors as first-class blocks; code appears in-panel as *identity* only, with the full text mirrored to an addon-owned `Text` datablock. **Two decisions here were reversed at the first human visual pass (2026-09-26)**: the bounded pager is **gone** (the whole transcript renders and the sidebar region scrolls), and the receipt moved under the streaming reply. Controls sit *above* the transcript so they cannot drift off the fold, and all prose wraps to the sidebar's actual width. Its Stop claim was also **half wrong** — a blocking C call never stops, but a pure-Python loop can once a call budget exists ([Runaway and hang protection](issues/17-runaway-and-hang-protection.md)).
- [The agent loop's control flow and failure policy](issues/09-agent-loop-and-recovery.md): a **per-tick state machine with exactly one tool call per timer callback** (a blocking round-loop could never draw the running state); caps of 8 rounds / 24 calls plus a repeat-signature stop and a consecutive-failure stop; partial application is **reported, never unwound**; nothing auto-retries.
- [What the prompt teaches the model about Blender](issues/10-system-prompt-and-blender-idioms.md): guidance split across a stable system prompt, per-tool descriptions and runtime RNA introspection — never a hand-maintained API list, which rots and outranks the live build; adds the `guide` kind to `get_rna_info`; corrects one-change-per-call from "individually revertible" to "legible and bounded".
- [How the addon talks to the API: worker thread or subprocess?](issues/11-http-transport-thread-or-subprocess.md): a **subprocess** — Blender's bundled `python3.13` via `sys.executable`, newline-delimited JSON over stdin/stdout, launch-to-ready in 0.021 s (IPC two orders of magnitude below one timer tick); the thread loses because the docs name that exact pattern as unsupported and every shipped Blender download uses a process.
- [What replaces undo as the recovery mechanism?](issues/12-recovery-mechanism.md): the memfile undo stack, **one push per user turn at the end in a `finally`**; the `.blend` copy demoted to opt-in and once per session; the before-image is a pre/post diff of the bounded `get_scene_info` summary, which is also the receipt the user sees; Global Undo off *pauses* auto-run rather than warning; and auto-run is **unscoped** — the demotion to scene-only with a full-power gate was **REJECTED by the project owner**, so §6's gate is *not built* (read the ticket's Ratification section for what that leaves in force).
- [The capability boundary for model-authored code](issues/13-execution-capability-boundary.md): the allowlist is specified as data and **installed as a reference implementation**, then attacked — `tools/capability_probe.py`, 77 attempts, **49 denied / 2 ESCAPED / 11 blocked / 15 allowed** (independently re-run and reproduced). The verdict is uncomfortable and worth reading: a two-line payload with no imports escapes, and the guard's own proxies leak their guts, so this is **hygiene, not containment** — ticket 12's "the promise becomes true rather than decorative" is amended. It also corrects ticket 12's capability list against the installed build: `Text.write()` is not a file capability and `bpy.ops.script.python_exec` does not exist in 5.2.2.
- [How a conversation degrades as context grows](issues/14-conversation-degradation.md): the store is the user's record and **degradation is a request-time projection that is never written back** — no model-authored summary; evict by cost × reconstructibility rather than age; measure in UTF-8 bytes of the wire JSON against a 48,000-byte budget. It also **supersedes ticket 09 §4's `messages[0]` live-summary form** (which destroyed prefix caching and contradicted ticket 10) in favour of a trailing `system` message, recomputed per request.
- [Confirm the four undo cases in a GUI](issues/15-undo-gui-confirmation.md): **the undo discipline was measured, and it holds.** One push at the **END** covers a whole multi-operation turn in a single Ctrl+Z; pushing at the **START** reverts *further back than the change it was meant to protect* — so the push-at-end rule survives the test designed to break it; and an unpushed change is not merely unprotected, because Ctrl+Z reaches **past** it and deletes the object. Global Undo off makes `bpy.ops.ed.undo()` **raise a poll failure** rather than silently no-op, so the preference is a valid detector *and* the push attempt is a second, mechanical one. **Edit mode is the dangerous case:** a push there returns ok, records nothing usable, and the following undo removes the object — so pushing in edit mode must be **refused**, not attempted. The real Ctrl+Z keypress behaves exactly as the operator does, and `undo_push(message=…)` labels appear verbatim in Undo History, so a turn can be labelled and found.
- [The first live send against DeepSeek](issues/16-first-live-send.md): **the wire contracts are measured, not assumed.** Seven requests, 11.6 s, under a cent. A `tool_call` with **no matching `tool` result is rejected, HTTP 400** — so ticket 09's synthetic `cancelled` results are load-bearing, not tidy. A **trailing `system` message is accepted**, so the live summary stays last, the base prompt keeps index 0 and its cache prefix, and ticket 14's fallback is unnecessary. Streaming works (41 SSE chunks, first at 0.04 s). The legacy model name `deepseek-v4-flash` is accepted while **silently serving `deepseek-flash`**. Two unasked findings: `tool_calls[].function.arguments` is a **JSON string**, and thinking is on by default and **billed as completion tokens** (25 of 64 in one probe), which both budget caps must absorb. Deferred: forcing a real `context_length_exceeded`, because the limit is 1M tokens.
- [Runaway and hang protection](issues/17-runaway-and-hang-protection.md): **the mechanism ticket 12 proposed does not work, and one that does was measured instead.** `sys.monitoring` `LINE` **cannot stop `while True: pass`** — a compiled one-liner's jump and target share a line, so it fires six times in 1.8 s and never interrupts. **SIGALRM stops the canonical loop, `time.sleep` and a blocking `recv` at 1.04× overhead**, which the monitor cannot do at all (4.4×/11.4× cost). Long native calls — `numpy`, a single `bpy.ops` — are stopped **only after they return** (5.34 s elapsed on a 1 s alarm), so the UI must never promise otherwise. Interrupt cost is clean when unswallowed: model `finally`, runner `finally` and the turn-end `undo_push` all run, on both paths. **And the guard is disarmable in one line:** `except BaseException` swallows all three mechanisms, `sys.monitoring.set_events(2,0)` and `signal.setitimer(ITIMER_REAL,0)` each disarm one, and post-turn depsgraph handlers run **unmonitored, unpushed and unreceipted**. Recommendation: wall-clock SIGALRM 15 s per call, 60 s per turn, LINE only as a cheap backstop.

- **How the panel shows what the agent changed in the scene.** *Answered by [What replaces undo as the recovery mechanism?](issues/12-recovery-mechanism.md) §3 and [How a conversation is laid out and controlled](issues/08-panel-conversation-ux.md) §5, pending ratification:* the pre/post bounded `get_scene_info` summary diff is the receipt, and it says "objects/data changed", not "exactly these properties changed". There is no textual diff for `bpy` mutations and none is needed. Kept here only so a human can see the claim.
- **Whether the agent should see the viewport** — screenshots or render feedback rather than only scene data. Deliberately deferred; only meaningful once the panel and loop exist.
- **Whether Blender's own Python surfaces** (Text Editor, Python Console) should be reused or ignored once the panel works. *Partly answered by [How a conversation is laid out and controlled](issues/08-panel-conversation-ux.md):* the Text Editor is the code-companion and the full-history escape hatch, bound to an addon-owned `Text` datablock — which makes that datablock a second leak vector to strip or label (flagged in *Where chat history lives*). What remains open is the Python Console.
- **What happens with more than one panel open** — *graduated by the second sweep to* [Whose state is it when more than one panel is open](issues/18-multi-panel-ownership.md). It stopped being fog once *How a conversation degrades as context grows* split the world into a store and a request-time projection: nothing decides who owns the projection, the in-flight turn, or the `_worker.py` child when a second panel appears.
- **Whether chaining models or base URLs mid-conversation is safe**, given providers differ in how they format tool calls already present in the history. *Sharpened, not graduated, by [How a conversation degrades as context grows](issues/14-conversation-degradation.md):* the store keeps messages verbatim **in provider wire format**, which is exactly what makes a mid-conversation provider switch risky rather than harmless — the history was written for one provider's dialect. Still fog because it cannot be answered without a live send; see *The first live send against a real provider*.
- **Whether a stuck turn can be stopped at all** — *graduated by the second sweep to* [Runaway and hang protection: what can actually be stopped](issues/17-runaway-and-hang-protection.md). Two tickets independently concluded that a blocking call cannot be interrupted and that the UI must say so; neither says what it says.

> **Left in the fog deliberately by the second sweep**, because the cap on graduating tickets is 3 and these are the least likely to be reached by the current slice: **whether the agent should see the viewport**; **the Python Console** (the Text Editor half is answered by *How a conversation is laid out and controlled*); **chaining models or base URLs mid-conversation** (annotated above); and **the second `Text` datablock leak vector**, which is now referenced by three tickets and owned by none.

## Out of scope

<!-- work ruled beyond the destination; closed forever unless the destination is redrawn -->

- **Any Node/TypeScript sidecar, or reusing `pi-mono` / `veoery/BlenderAgent`'s runtime.** Judged beyond this slice: the in-process Python loop reaches the destination without IPC, and forking a TS monorepo buys machinery (managed workspaces, iteration artifacts, render critique) the slice deliberately excludes. Returns only as a fresh effort if the in-process loop proves insufficient. (A *Python* worker subprocess carrying only HTTP is a different thing and is live in *How the addon talks to the API: worker thread or subprocess?* — that is transport, not an agent runtime.)
- **Headless / `blender -b` operation.** The design depends on the GUI event loop — timers and modal operators never fire in background mode — so a panel-driven agent cannot work there by construction.
- **A VS Code extension, or any chat client outside Blender.**
- **Modifying the Blender source tree** — C++ or in-tree Python.
- **Rendering and visual-iteration tools** (`save_view`, `render`) and the workspace/iteration artifact model.
- **Multi-provider abstraction** (Anthropic-native, local models). One OpenAI-compatible backend only.
- **Blender 5.3-alpha support** and multi-version compatibility shims.
- **Distribution** — publishing to extensions.blender.org, supporting other users, token/cost accounting.
